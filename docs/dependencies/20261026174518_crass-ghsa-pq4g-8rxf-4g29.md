# crass GHSA-pq4g-8rxf-4g29

## Dependency

- crass (was 1.0.7, now 1.0.8)
- Constraint in this repo: none in the gemspec. Transitive via actionview, rails-html-sanitizer 1.7.1, and loofah 2.25.2 (crass ~> 1.0.2).
- Lockfiles: Gemfile.lock, gemfiles/rails72.gemfile.lock, gemfiles/rails8ruby34.gemfile.lock, gemfiles/rails8ruby4.gemfile.lock

## Symptom

bundler-audit matches crass 1.0.7 against GHSA-pq4g-8rxf-4g29. make release stops on gemfiles/rails72.gemfile while that pin remains.

## Evidence

- Advisory: the tokenizer kept consuming a bad URL after an escaped backslash when the next code point was ). A browser ends the bad URL there. A CSS sanitizer that re-emits Crass tokens can pass through declarations, style rules, or at-rules it meant to drop. Affected <= 1.0.7. Patched 1.0.8. Published 2026-10-21. Severity on the advisory page: Moderate, 5.3. The page did not list a CVE ID.
- Confirmed impact names Sanitize, Loofah::HTML5::Scrub.scrub_css, and rails-html-sanitizer sanitize_css / sanitize when style is permitted.
- Installed crass 1.0.8 Tokenizer#consume_bad_url treats ) as the end of a bad URL unless the next two unconsumed code points are a valid escape.
- This tree has no scrub_css or sanitize_css call. ActiveAdmin's CSV sanitizer prefixes a quote for spreadsheet injection. It does not call Loofah.

## Suggested fix

Upgrade lockfiles to crass 1.0.8. loofah ~> 1.0.2 already allows that patch. Leave crass off the gemspec.

## Applicability

- Vulnerable component was present in the pre-fix lockfiles at 1.0.7, reached through actionview -> rails-html-sanitizer -> loofah.
- Exploit conditions require untrusted CSS parsed and re-emitted by a Crass-based sanitizer. That call is absent in this tree and in ActiveAdmin's CSV sanitizer.

## Priority

- This repository's execute path: low. The CSS re-emit path named by the advisory is not called here.

## Disposition

- Upgrade. bundle lock --update=crass --patch --conservative on the root Gemfile and each appraisal gemfile. Resolved 1.0.8. No gemspec floor.
